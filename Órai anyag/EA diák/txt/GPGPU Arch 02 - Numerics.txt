IEEE 754-1985
●   Rounding modes:
     ○   Round to {minus infinity, plus infinity, zero, nearest}
     ○   Round to nearest has a tie-breaker such that the nearest even number should be returned (it
         is often called round-to-nearest-even)
IEEE 754-1985
●   Initially, rounding direction was meant to be a global state
    (usually, modern CPUs use per micro-op attributes instead)
●   Some methods switch between them often (e.g. interval arithmetics)
●   However, in pipelined systems this incurs an extra cost: the fp pipelines need
    to be flushed before altering the rounding
●   These may be circumvented by some useful identities
IEEE 754-1985
●   Operations:
     ○   The results of the following operations have to be correctly rounded: +, -, *, /, sqrt
     ○   Correctly rounded means wrt. the floating point representation of the exact result
●   Conversion to and from decimal strings
●   Floating point exceptions: invalid, division by zero, overflow, underflow,
    inexact
     ○   Either calling a trap or setting a status flag
Floating point numbers VS real numbers
●   + and * are commutative:
         fl(a + b) = fl(b + a),
         fl(a*b) = fl(b*a)
●   + and * are not associative:
         fl(a + fl(b + c)) != fl(fl(a + b) + c)
●   + and * are not distributive:
         fl(a * fl(b + c)) != fl(fl(a*b) + fl(a*c))
●   0.0 * x != 0.0
●   fma(a, b, c) != fl(fl(a*b) + c)
IEEE 854-1987
●   Radix-independent formulations
●   Various ‘hotfixes’
IEEE 754-2008
●   Merged the two previous standards and also incorporated two decades worth
    of hardware evolution
●   Algorithmic and theoretical improvements made certain prescribed precision
    constraints overly relaxed
●   Fused multiply-add (FMA) standardized:
     ○   fma(a, b, c) = fl(a*b + c), that is, it only uses a single rounding, a*b is kept at higher precision,
         where fl(x) is the floating point representation of the real number x
     ○   This single instruction makes writing robust code much easier
●   Also added a lot more (quadruple types, etc.)

inline float DifferenceOfProducts(float a, float b, float c, float d) {
    float cd = c * d;
    float err = std::fma(-c, d, cd);
    float dop = std::fma(a, b, -cd);
    return dop + err;
}

FMA in MSVC - in practice
●   Simply using std::fma achieves no performance gains - if you don’t set up
    your project properly, you will end up with extremely expensive calls to a
    software FMA implementation
●   You need two things for std::fma to amount to actual CPU instructions:
     ○   use optimizations (/O2)
     ○   set architecture to AVX2 (/arch:AVX2)

Math modes in MSVC
●   Floating point mode docs:
    https://learn.microsoft.com/en-us/cpp/build/reference/fp-specify-floating-point-
    behavior?view=msvc-170
●   Main modes:
     ○   Precise: this is the default. Rounding happens at 1) assignment 2) typecast 3) argument
         passing to function call 4) return from function call. Conformal to IEEE 754. However, the
         compiler assumes that the user is not changing rounding modes.
     ○   Strict: more restricted that precise, the compiler has to place extra code to trap floating point
         exceptions, etc. The former can be also achieved by turning fp:except on.
     ○   Fast: similar to fast math on GCC.
●   Contract: allows the compiler to inject FMAs for precise mode.

Numerical disasters
●   The Patriot Incident:
     ○   February 25, 1991 - a Patriot battery failed to neutralize an incoming Scud missile, resulting in
         the death of 28 soldiers and the injury of 100
     ○   This was caused by a numerical error:
           ■ The system counted the elapsed time since boot in tenth of seconds
           ■ It multiplied this number by 1/10, represented in 24 bit fixed point precision
           ■ The battery had been online for 100 hours - it’s imprecision was at about 0.34 seconds
           ■ A Scud missile travels at about 1600-1800 meters per second
     ○   The situation was made worse by partial numerical improvements - always roll out full updates
●   More: https://www.iro.umontreal.ca/~mignotte/IFT2425/Disasters.html
