Execution on the GPU
 ●   GPUs batch threads and these batches and
     their sets are the units of scheduling
 ●   The batches are called wavefronts on AMD      Wavefront x32
     (and warps on NVIDIA GPUs)
 ●   A wavefront consists of 32 or 64 threads -
     the number is the wave mode
 ●   Wavefronts may be bundled into thread- or
     workgroups (up to 32 wavefronts) that share   Wavefront x64
     certain GPU resources and threads within
     one group can communicate/sync cheaply

WGP caches - I$
●   L0 instruction cache is shared between all 4 SIMD32s
●   It is divided into 4 banks, each of which can supply 32 bytes of data 24 instructions)
●   Each bank contains 128 cache lines
●   An I$ cache line is 64 bytes
●   The instructions are forwarded to the SIMD32 wavefront controllers, that have 20
    instruction pointers
WGP caches - K$
●   More precisely, the constant scalar cache
●   16 KB 4-way associative cache
●   Shared by all 4 SIMD32s within the WGP
●   Split into 2 banks
●   Each bank contains 128 cache lines
●   16 bytes per clock to the SGPR register file
WGP caches - V$
●   16KB 4-way associative, write-through LRU cache
●   Two busses from the vector cache to the SIMD32s
●   Each bus is capable of submitting 32 addresses
●   Memory requests are coalesced (grouped together) based on which ones address the
    same 128 bytes long cache line
●   Response bus can deliver 128 bytes per cycle 4 bytes per wave in wave32 mode)
●   RDNA specific: texture fetches go the same path as texture loads, providing smaller
    latency and larger throughput 35% and 8x, respectively, in RDNA) as long as they are
    not mixed with texture samples

Variables
 In relation to the wavefront as a unit, there are two types of thread variables:
  ● Scalar (wavefront invariant, same for all threads) ⇒ up to 108 per wavefront
  ● Vector (local, unique to each thread) ⇒ up to 256 per thread

 These are physically different pieces of memory. Each SIMD32 has
  ● a 128204 byte SGPR and
  ● a 1024324 byte VGPR
 register table.

 The allocation granularity of physical VGPRs is 8. It means that the logical
 allocation granularity is
   ● wave32: 8
   ● wave64: 4
VGPR
  ●   VGPRs are split into 4 banks
  ●   Different registers are mapped to different banks via some
      (undisclosed) heuristics, like v[k] to bank k%4, etc.
  ●   Each bank can be accessed only once per cycle (1 read, 1 write)
  ●   Subsequent requests will force serialization
  ●   There are some caches that may be able to optimize this away
  ●   And this is true to everything that is split into banks
Wave32 VS wave64
  ●   By default, only pixel/fragment shaders are wave64
  ●   A wave64 wavefront consists of up to 64 threads ⇒
      their local variables require 644 bytes of data
  ●   Wave64 VGPRs are backed by 2 physical VGPR
      registers ⇒ very expensive!
  ●   Operations on wave64 workloads also take twice as
      many clocks to execute
  ●   Subvector execution can mitigate VGPR pressure
      due to wave64
  ●   Modern shading languages expose wavesize
      settings

Occupancy VS LDS
  ●   The 4 SIMDs share a 128KB LDS
  ●   Up to 420 wavefronts content for this space
  ●   The shared and groupshared variables are
      per-threadgroup
  ●   A threadgroup may allocate up to 32KB from
      the LDS as per DX specifications - but that
      would limit occupancy (severely)
  ●   Exact mechanics for this are NDAʼd but profilers
      will let you uncover the magic numbers
VGPR and SGPR initial values
  ●   Certain values are preloaded into VGPRs and SGPRs,
      depending on the shader type
  ●   There are also 32 SGPRs free for grabs (the actual place
      of root/push constants in DX12/Vulkan)
  ●   In the above example: s2 was pre-loaded with the LDS
      address of the parameter cache
  ●   There are also some special registers that serve a
      specific purpose and are oftentimes read implicitly by
      various instructions

Constant folding
  ●   Always compute these things on the CPU and push it into a constant
      buffer/uniform object buffer
  ●   It makes no sense to compute something 2073600 times per frame instead
      of once - even if that once has to be on the CPU
  ●   Similarly, avoid using texture dimension query semantics at all costs. Those
      are expensive operations. You are setting the textures so you might as well
      send in their dimensions as well and spare yourself from taxing the L0
      cache
Constant folding with FMA in mind
  ●   You often map data x from 0,1] to [a, b]
  ●   The canonical transform is x*(b-a) + a
  ●   This could be a FMA
  ●   So donʼt store a and b in the uniform
      buffer, store (b-a) and a instead!
Constant folding with FMA in mind
  ●   Similarly, mapping x from [a,b] to [c, d] is mathematically
      (x-a)/(b-a) * (d-c) + c
  ●   Again, this could be a single FMA
  ●   The math is a bit more lengthy here:
      x*(d-c)/(b-a) - a*(d-c)/(b-a) + c
  ●   But the end result is that put these into your uniform buffer and
      follow with an FMA (d-c)/(b-a), - a*(d-c)/(b-a) + c
