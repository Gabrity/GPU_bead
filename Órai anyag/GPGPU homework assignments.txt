6. Simulation of the depth of field (up to 105%)

A  summed-area        table  (SAT),    also  called   an
integral image    is a 2D table generated from an
input  image    in which    each   entry   in the  table
stores  the  sum   of all  pixels  between    the  entry
location  and   the  lower-left   corner   of the  input
image.   The   power    of  the  summed-area       table
comes    from   the   fact  that  it can   be   used   to
perform   filters of different  widths at   every pixel
in  the   image     in   constant    time    per   pixel.
Generating       a   box-filtered     pixel   using    a
summed-area        table   requires     sampling     the
summed-area table at the four corners of a
rectangular filter region, sur, sul, sll, slr.




where    w  and    h  are the    width and height       of  the filter  kernel,   and sur is   the upper-right
corner sample, sll is the lower-left corner sample, and so on. We can use this technique
for  variable-width      filtering,  by   varying    the  locations     of  the  four   samples      we   use   to
compute each filtered output pixel.

Tasks:
    ●   Input:
             a.  Read a pair of input RGB and depth images (5%)
             b.  OR   use real-time OpenGL/DX/Vulkan rendering of a scene with color and depth
                 rendered to frame buffers directly (15%).
    ●   Use the Scan parallel pattern to implement the Summed-Area Table. (20%)
    ●   Use the variable-width box filter to compute the smoothed image. (20%)
    ●   Save the output image to a file. (5%)
    ●   Use real-time display (20%) and change the parameters for focus in real-time. (20%)
        [0% without interoperation and memory sharing]]

9. Fast Graph Cuts on the GPU (up to 125%)

Graph    cut  optimization    finds   the  global   minimum     to  a  specific   energy    (i.e., global  energy
minimization),    if the energy can     be represented      by  the  so-called flow graph, thus solving the
problem    through graph optimization to        find the max flow between         a source    and   a sink node.
Some problems  in computer vision solvable using Graph cuts:











     Stereo depth estimation                          Foreground-background segmentation
There   are a  number     of graph cut algorithms,       such as   the Ford-Fulkerson (solved on a global
scope   based    on   search   trees),  and   the  Goldberg-Tarjan      “push-relabel”    algorithm.   The   latter
considers a single node of the graph at a time, thus works on a local scope interacting only with
direct neighbors. This is inherently parallel and a perfect fit for a GPU implementation.

Implement the Goldberg-Tarjan algorithm on regular graphs with 4-neighborhood (i.e., 2D grids,
or   considering     4-connectivity      of   neighboring      pixels    in   an    image),    and     solve    the
foreground-background segmentation problem.
    ●   Naive CPU implementation. (10%)
    ●   Naive GPU implementation. (30%) Compare runtime to the CPU implementation (5%).
    ●   Apply the implementation(s) to foreground-background image segmentation. (20%)
    ●   Apply your implementation to a different problem of your choice. (+20%)
    ●   Extra    points   for  demonstrated      improvements       over    the  naive   GPU     implementation
        (runtime comparison, GIT-documented changes to the codebase). (30%)
        (Tips: improve relabel through “wave”-push operations, compress residual edges using a
        bit-vector,   periodic   global   relabeling,   use   workgroups      for  tile-based   push-relabel    by
        splitting the graph to e.g. 32×32 tiles, exact global relabeling, etc.)
    ●   Compare runtime to the Boykov-Kolmogorov algorithm (e.g. the maxflow library). (10%)
Note that the task cannot be accepted without a working parallel implementation.
Readings:
    ●   Timo Stich's presentation - Graph Cuts with CUDA (2009, GPU Technology Conference)
    ●   "Fast Graph Cuts for Computer Vision" in GPU Computing Gems, Emerald Edition
    ●   Wikipedia - Goldberg-Tarjan “push-relabel” algorithm
    ●   A V. Goldberg and R. E. Tarjan - A New Approach to the Maximum-Flow Problem (1988)

10. Fast Convolution on GPUs (up to 40+20=60%)


The goal is to optimize the convolution step of a neural network.

The input data is a set of 2D images (w x h) that has a depth (d) (or number of channels), that is
to be convolved with a set of filters (N_F) that has size (wf x hf) and a matching depth. During
convolution, we sum over the depth, but keep the dimension of the set of filters, so the output is
a set (N_F elements) of 2D images with width: ((w - wf + 1) x (h - hf + 1)).

A reference CPU version is provided, the code only has to work for the specific sizes provided in
the       reference        implementation           and        the       reference        input/output         files:
http://u235axe.web.elte.hu/GPUCourse/Convolution/

In      the        GPU         implementation,           use        the       fast       Winograd          method
(https://arxiv.org/pdf/1509.09308.pdf),        utilize  shared    memory     and   textures    to accelerate     the
computation     as much    as   possible.   Always check that the computation is valid on the provided
reference output file. The maximum element wise error should be smaller than 3e-5f.

A single   correct  implementation gives 40%, a series of implementations showing how different
optimizations improved (or not improved) performance with a small documentation of the ideas
behind the different approaches can give an additional +20%.

12. Raytrace the rainbow on the GPU (up to 80%)

Rainbow is formed as rays coming from the sun refract and reflect on rain droplets. This can be
easily  computed      in the   following   way:   assume     a  set  of parallel   rays  coming     from  a  certain
direction  toward a    sphere    of water. Compute the intersection of each ray with the sphere, and
compute     the  normal    of  the  sphere     at the   intersection   point.   Snell's  law   gives   the  relation
between    the angle    of  incidence   and   the angle    of  refraction  for a  given index-of-refraction (n).
However,    n  is dependent     on the wavelength of the         light so   different  colors  refract at different
angles. Follow     the  light rays  until at most 4 intersections with the sphere or until they leave it,
and set up a virtual screen plane on the opposite side with respect to the sun, and calculate the
intersection of rays with the plane and record the number of rays at certain pixels including their
wavelengths. Convolve         with the color matching functions to get RGB values, display the result
on     the     virtual    screen       as    an      image      file    (as    png      or     jpeg,     see     eg.:
https://github.com/nothings/stb/blob/master/stb_image_write.h) or with OpenGL on the screen.

Try to follow multiple rays with each thread (vectorize) to improve performance.

Grading:
    ●    Correct implementation of the 3D geometry and refraction/reflection computation on the
         GPU (30%)
    ●    Correct implementation of the color conversion from wavelengths to RGB values on the
         GPU (15%)
    ●    Correct   implementation      of  a  vectorized version and performance comparison                 with  the
         non-vectorized one (+5%)
    ●    Color display as a static image file (+5%)
    ●    Color display with OpenGL on the            screen,   with  interactively changeable viewing angle
         (+10%) [0% without interoperation and memory sharing]]

For  additional    +15%    compute     the   intensity   changes     properly   at  the  intersections    using   the
Fresnel equations assuming unpolarized light.

13. Estimate Height Map from Normal Map (.. 120%)

In Computer Graphics        the micro    geometry is    rendered with the help        of Normal Map textures.
The  pixels  of a normal map describe normal coordinates,               so  when    it is applied to a rendered
surface, the   surface   normal    can be    perturbed by the fetched coordinates in Frenet-frame. It is
wide-spread method, but has some drawbacks. Therefore nowadays Height Map representation
is used.    It means     that   instead   of   normal    vectors,   the   texture   simply   contains    a  height
perturbation    in  surface   normal    direction.   The   normal    map    can   be  computed      on-the-fly   by
numerical derivation.

In practice we can assume, that any normal map “comes” from derivation of a height map scalar
                             ∂𝑥𝑆×∂𝑦𝑆
field, in a way that 𝑁   =   |∂𝑆×∂ 𝑆| , where 𝑁 is the resulting normal vector, 𝑆 is the scalar
                              𝑥    𝑦
field. Also, 𝑁’s   coordinates are between -1 and 1. In order to store them in a texture pixel, the
coordinates are linearly transformed to the span of 0..1.

The   task   is, that  for  an   input  Normal     Map    the  application    should   estimate    the  assumed
underlying scalar field. We do not need to handle and surface non-linearity, simply we can work
in a rectangular parametric space (e.g. texture coordinates).

The solution:
The   “traditional”  solution    is that  a  Poisson-system        is established,     where    the  unknown is      the
scalar-field.  Solving    the system     (and potentially a      scale normalization)       gives   the  estimate    we
want.
